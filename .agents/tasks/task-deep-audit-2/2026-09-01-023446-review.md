# Escape scraped map data and dynamic toast text against DOM-XSS (v1)

This change remediates the second-pass audit's CRITICAL C-1 (attribute-breakout DOM-XSS in the maps-rating modal) and HIGH H-1 (dynamic `showToast` innerHTML). It introduces a pure, unit-tested `helpers/htmlEscape.js` as the single source of truth for renderer-side escaping, exposes it through the preload `contextBridge` as `window.htmlEscape.escape`, aliases it in `front.js`, and applies it to the scraped `mapName`/`skill_group` before they enter the `.show-maps` `innerHTML` template and to the login/username + `ret.error` substrings at the three dynamic `showToast` call sites. The escaping is deliberately a no-op for legitimate Steam data, so normal rows and toasts render identically.

Watch for: **one scraped sink in the same handler was missed (confirmed).** The `<img src="${mapIconPath}">` interpolation still receives the *raw* map name — `getMapIconPath` returns `img/maps-icons/${mapName}.svg` verbatim for any name beginning `de_`/`ar_`/`cs_`, so a scraped name like `de_x" onerror="alert(1)` breaks out of the `src` attribute exactly as the C-1 payload breaks out of `alt`/`title`. The fix closed `alt`, `title`, and the text node but left this fourth sink, which is the same attribute-breakout vector the change set out to eliminate and which the audit's own C-1 sink listing and FEAT-002 acceptance step ("no unescaped scraped value reaches innerHTML") both cover.

**Verdict**: NEEDS_CHANGES

## High-level view

The escaper is routed through a single `helpers/htmlEscape.js` consumed by both preload and the unit test, which removes the drift risk a duplicated renderer-local copy would carry — the "one implementation to test" goal is met.

C-1 is only *partially* remediated. Three of the four scraped sinks in the `.show-maps` `innerHTML` template are now escaped (the map-name text node, the `alt`, and the `title`), but the `<img src>` for the map icon still interpolates the raw `mapName` via `getMapIconPath`'s `de_`/`ar_`/`cs_` fallback branch. Because the GCPD regex capture (`[^<]+`) admits `"`, spaces, and `=`, a hostile prefixed name breaks out of `src` and injects an event handler — the identical exploit class C-1 describes. This is the blocking issue.

H-1 is handled correctly and narrowly: only the dynamic login/error substrings are escaped, and `showToast` keeps `innerHTML` so the intentional static update-link toast still renders its anchor.

Test coverage proves the helper but not the wiring. The 10 cases exercise the real `escapeHtml`, including the exact `x" onerror="alert(1)` breakout payload, and would fail if the escaper's logic were reverted. They do not assert that `front.js` calls the escaper at each sink, so a regression that dropped the `mapNameSafe`/`skillGroupSafe` calls (or the still-missing `src` escaping) would pass unnoticed — a limitation given there is no DOM harness.

The audit's severity calls and FALSE POSITIVE list hold up against the code: the markdown-it `html:false` path, the `.innerText` account cells, defensive `protoDecode`/`protoEncode`, AES-256-GCM storage, the irreducible `COMPETITIVE_MAP_ROW_SOURCE` gaps, and the `wins_dz` asymmetry are all correctly characterized as safe/intentional and were not disturbed by this change.

### The missed `src` sink: same breakout, different attribute

The `.show-maps` handler computes `mapIconPath` from the raw name and then interpolates it into the icon cell:

```js
const mapIconPath = getMapIconPath(mapName);   // raw mapName
...
${mapIconPath ? `<img src="${mapIconPath}" alt="${mapNameSafe}" ... onerror="this.style.display='none'">` : ''}
```

`getMapIconPath` returns a fixed path from its dictionary for known maps, but its fallback is:

```js
if (mapName.startsWith('de_') || mapName.startsWith('ar_') || mapName.startsWith('cs_')) {
  return `img/maps-icons/${mapName}.svg`;
}
```

The GCPD parser captures the map name with `<td>([^<]+)</td>` (`COMPETITIVE_MAP_ROW_SOURCE`), which blocks `<` but not `"`, space, or `=`. A scraped name `de_x" onerror="alert(1)` therefore:

1. passes the `de_` prefix check,
2. yields `mapIconPath = img/maps-icons/de_x" onerror="alert(1).svg`,
3. is interpolated into `src="img/maps-icons/de_x" onerror="alert(1).svg"`, closing the `src` attribute early and injecting an `onerror` handler that fires when the (now bogus) image path fails to load.

This is the exact attribute-breakout the change escaped out of `alt`/`title`/text — it simply also reaches `src` through the icon-path indirection, and that indirection is why the raw value is still live. The fix's NOTE ("`getMapIconPath` is keyed off the RAW mapName so the icon lookup still resolves") correctly keeps the *lookup* on the raw value, but the *result* of that lookup carries the raw name into the template unescaped. The fix is to keep the lookup on raw `mapName` and escape the returned path (a no-op for legitimate names — real paths contain none of the escaped characters), or escape the fallback's `mapName` inside `getMapIconPath`, or build the icon cell with `setAttribute('src', ...)`. Confidence: confirmed — the capture class, the prefix branch, and the interpolation are all present and traced end to end.

The dictionary branch is not exploitable (its values are hard-coded filenames), so only the prefixed fallback is the live path; a regression test should use a `de_`/`ar_`/`cs_`-prefixed breakout name specifically, since the existing `x" onerror="alert(1)` payload hits the empty-string return and never exercises `src`.

### Escaper design and single source of truth

`escapeHtml` replaces `& < > " '` with entities, coerces via `String(value)`, and returns `''` for null/undefined — sufficient for both quoted-attribute and text-node contexts, which are the only sinks in scope. Routing preload and the test through the same `helpers/htmlEscape.js`, rather than a renderer-local duplicate, is what eliminates the drift risk the FEAT-002 spec warned about; there is exactly one implementation and it is the one under test. The `front.js` alias depends on the preload bridge being present, which it is for the packaged renderer.

### H-1 toast hardening

The three dynamic call sites (`login + ret.error` and the two `username.value + ret.error` handlers) escape both substrings, while `showToast` keeps `innerHTML` so the static update-available toast (`<a ... download it here</a>`) still renders as markup. No remaining dynamic `showToast` call site interpolates unescaped external data — the copy/status toasts use static literals. Confidence: confirmed.

### Regression tests

The suite imports the real `escapeHtml` and asserts the entity mappings, null/undefined → `''`, numeric coercion, benign map names passing through unchanged, and the `x" onerror="alert(1)` breakout reducing to `x&quot; onerror=&quot;alert(1)` with no surviving raw `"`. Reverting the escaper's `.replace` would fail these. What no test covers is that `front.js` actually invokes the escaper at each sink — dropping `mapNameSafe`/`skillGroupSafe` (or leaving the `src` sink raw) is invisible to the suite. This mirrors the audit's own note that a front.js integration test needs a DOM harness; the manual re-read step in FEAT-002 should not be treated as replaced by the unit tests.

### Invariants and false-positive list

Nothing in the diff touches the hard invariants the briefing enumerates: EncryptedStorage AES-GCM, GC message-ID/field handling, `protoDecode`, the rank state machine (expired mm/wg/dz, premier `rank_premier===-1`, VAC cascade, GCPD gap-filler never clobbering `-1`), the XP formula, the markdown-it `html:false` path, and the `renderRowRanks` `wins_dz` bare-vs-`?? 0` asymmetry with its DOM write order. The change is confined to escaping at interpolation boundaries plus the new helper/preload wiring. The audit's FALSE POSITIVE entries (markdown `html:false`, `.innerText` cells, absent `eval`, defensive proto codec, navigation guards, GCM crypto, `sandbox:false` rationale, `resolveHelloPenaltyReason` sentinel, regex gaps, `wins_dz` asymmetry) each match what the code actually does. The escalation of C-1 to CRITICAL (renderer XSS gaining full variadic IPC reach through the preload surface) is defensible given the exposed `ipcRenderer.send/on/invoke` bridge.
