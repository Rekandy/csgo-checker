# Escape map-icon `src` path to close the last DOM-XSS breakout in the maps modal (v2)

The v1 review returned NEEDS_CHANGES on a single blocking issue: the `.show-maps` maps-rating modal in `html/js/front.js` escaped the scraped map name and skill group into the text-node, `alt`, and `title` sinks, but left the map-icon `<img src="${mapIconPath}">` carrying the **raw** scraped map name. `getMapIconPath`'s `de_`/`ar_`/`cs_` fallback returns `img/maps-icons/${mapName}.svg` verbatim, and the GCPD row regex (`<td>([^<]+)</td>`) blocks `<` but not `"`, space, or `=`, so a scraped name like `de_x" onerror="alert(1)` broke out of the `src` attribute and injected an `onerror` handler — the same DOM-XSS class as the already-fixed sinks. The follow-up commit (`1081896`) adds `const mapIconPathSafe = escapeHtml(mapIconPath)` and interpolates that into the `src`, keeping the `getMapIconPath` lookup on the raw name so legitimate icons still resolve. A regression case and a no-op case were added to `test/htmlEscape.test.js`.

Watch for: the new regression test is a unit test on the `escapeHtml` helper, not a DOM-harness test — it asserts the escaping *behavior* but would not fail if the `front.js` `mapIconPathSafe` wiring itself were reverted (possible). This is the same untested-integration gap the v1 review noted as non-blocking, now also applying to the src sink. It does not block, since the src fix itself is confirmed by reading the code.

**Verdict**: APPROVED

## High-level view

All four scraped sinks in the `.show-maps` handler are now escaped. The map name reaches a text node and the icon `alt`; the skill group reaches the rank-image `alt` and `title`; the icon path reaches the icon `src`. The first three were closed in `3f8f99b`; the follow-up closes the fourth by escaping the returned icon path at the interpolation boundary. The second `<img src="${getRankImage(rank, 0, 'mm')}">` is not a scraped sink — `rank` is a `Number.parseInt` of a `\d+` capture and `getRankImage` builds its path from a fixed prefix table plus that integer, so no scraped string reaches it.

The lookup that decides *which* icon to load still runs on the raw name, so resolution is unchanged; only the string that lands in the attribute is escaped. `escapeHtml` rewrites only `& < > " '`, none of which appear in real icon paths like `img/maps-icons/de_dust2.svg`, so icons render byte-identically.

The follow-up touches only `html/js/front.js` (one line plus a comment), `test/htmlEscape.test.js`, and a findings JSON. None of the invariant-bearing modules (EncryptedStorage AES-GCM, GC message-ID/field handling, `protoDecode`, the rank state machine, XP formula, markdown-it `html:false`, `renderRowRanks`) are in the diff, so those invariants are structurally untouched by this pass.

### The fourth sink is now closed

The handler computes the icon path once from the raw name and reuses it for two distinct purposes:

```js
const mapIconPath = getMapIconPath(mapName);        // raw name -> lookup (resolution)
const mapIconPathSafe = escapeHtml(mapIconPath);    // escaped   -> attribute value
...
${mapIconPath ? `<img src="${mapIconPathSafe}" alt="${mapNameSafe}" ...>` : ''}
```

The `${mapIconPath ? ... : ''}` guard still tests the **raw** path, but that is a boolean truthiness check only — `getMapIconPath` returns `''` (falsy) for unknown names, so the guard only decides whether the `<img>` is emitted at all and is never an HTML sink. The only value that enters markup is `mapIconPathSafe`. The exploit path (`de_`/`ar_`/`cs_` prefix → fallback embeds the raw name → breakout) is closed because the string interpolated into `src=` is now escaped, turning `de_x" onerror="alert(1).svg` into `de_x&quot; onerror=&quot;alert(1).svg`, which cannot terminate the attribute.

`getRankImage(rank, 0, 'mm')` in the sibling `<img>` is not a scraped sink: `rank` comes from `Number.parseInt(/\d+/.exec(mapData.skill_group)[0], 10)`, and `getRankImage` composes `img/skillgroups/<prefix><integer>.svg` from a fixed prefix table. No attacker-controlled substring reaches that `src`.

### Regression test exercises the escape behavior but not the wiring

The added test asserts on the exact string the `de_`-prefixed fallback produces:

```js
const rawIconPath = 'img/maps-icons/de_x" onerror="alert(1).svg';
assert.strictEqual(escapeHtml(rawIconPath), 'img/maps-icons/de_x&quot; onerror=&quot;alert(1).svg');
```

The payload starts with `de_` (without a recognized prefix `getMapIconPath` returns `''` and the sink is never reached), so it mirrors the real exploit shape, and the no-op case (`de_dust2.svg` unchanged) pins the behavior-preservation claim. What it does not do is drive `front.js`: it calls `escapeHtml` directly, so it proves the helper neutralizes the breakout but not that the handler routes the icon path through the helper. Reverting `src="${mapIconPathSafe}"` back to `src="${mapIconPath}"` would leave all 145 tests green. That gap is the same one flagged non-blocking in v1 for the text/alt/title sinks; it is acceptable here because the wiring is confirmed by direct reading, but it is the one thing a future refactor could silently undo.

The follow-up diff is confined to the one `front.js` line, its comment, and the test file, so the AES-GCM storage, GC/rank/XP, protobuf, and markdown invariants are outside the change set and remain as verified in prior passes.
